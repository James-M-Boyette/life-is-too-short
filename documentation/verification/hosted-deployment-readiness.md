## 4. Native authorization-probe security gate

The tested Realtime read-authorization protocol creates a synthetic private=false, payload/event/binary-payload-null probe, reads it in the same transaction under JWT claims, then rolls back. Normal notification reads require private=true. The compatibility exception additionally matches owner **and** requested topic and current-transaction xmin; clients have no reserved-topic publishing policy. This is version-sensitive, not generic permission to read public messages.

Before installation, independent database/security review must match actual native send/topic signatures, owner, invoker behavior, function bodies and managed authorization protocol to the tested model. Repeat on an appropriately isolated version-matched stack: owner join/delivery; explicit B/anon/guessed denial; committed/nonprivate payload and marker denial; same-transaction owner-only empty probe; malformed sender/version/event denial; REST/websocket/SQL forging; partitions and alternate APIs. Review transaction-ID casts/frozen tuples/retention assumptions. Verify temporary SET/schema CREATE are removed and helpers cannot be assumed/inherited/executed by API roles; trusted migration-role ADMIN-only membership is a separate capability.

Enabled GraphQL is a particular outstanding gate: prior real proof had GraphQL disabled. Audit its actual table/function reachability as well as REST schemas; previously observed platform realtime.subscription grants must not acquire an unreviewed access path. Do not expose realtime/helper schemas, weaken RLS/private checks or permanently elevate the helper to make joins pass. A future hosted positive/negative fixture check must test **actual delivery**, not just SUBSCRIBED.

Public sources checked November 9, 2026; **the application's actual plan and configured limits remain unknown**. Published [Realtime limits](https://supabase.com/docs/guides/realtime/limits) list:

| Plan/configuration | Concurrent connections ceiling | Messages/second | Joins/second |
| --- | ---: | ---: | ---: |
| Free | 200 | 100 | 100 |
| Pro | 500 | 500 | 500 |
| Pro without spend cap / Team | 10,000 | 2,500 | 2,500 |

Project overrides/support arrangements can differ. These are throughput/connection limits, **not monthly billing allowances**. Documentation describes disconnection/reconnect after throughput falls; our joined-status gap still demonstrates that observed client status alone cannot establish delivery. The local MessagePerSecondRateLimitReached observation does not identify a hosted plan or exact local threshold.

Published [Realtime pricing](https://supabase.com/docs/guides/realtime/pricing) lists 2 million included messages on Free, 5 million on Pro/Team, paid overage $2.50 per million; included peak connections 200/500 respectively, paid overage $10 per 1,000. [Message accounting](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages) counts a Broadcast send plus receiving subscribers, rounding chargeable message packages up. No actual subscription, unused allowance or invoice is inferred.

Use W row invalidations and D receiving devices: approximate messages `W × (1+D)`; sum per owner for transfers. Project deletion moving K tasks sends K hints; debounce does not reduce those sends. Hidden connected tabs may still receive/bill notifications even though their API safety reads pause. Example assumptions: 5 users × 100 writes/day × 20 days × (1+2 devices) ≈ **30,000 messages**; 10 × 200 × 30 × 3 ≈ **180,000**. Conversely, a fast 5,000-row burst can generate 5,000 sends and up to 10,000 recipient deliveries—monthly averages cannot protect that peak. Actual rate window/configuration must be measured, not inferred from those totals. Project-wide limits mean one account's bulk activity can degrade others' availability without exposing their data; a written beta policy is not an enforced per-account quota.

For safety reads, let visible client-hours be `U × D × H × active_days`. Every such hour produces 30 complete snapshots, each `ceil(N/500)+1` requests for nonempty accounts. The Stage 3 short-title/null-description decoded-body samples yield:

| Assumed beta / account size | Safety GETs/month | Decoded safety response GB/month |
| --- | ---: | ---: |
| 5 users, 2 devices, 2 h/day, 20 days; 100 tasks | 24,000 | 0.46 |
| Same usage; 1,000 tasks | 36,000 | 4.58 |
| Same usage; 5,000 tasks | 132,000 | 23.00 |
| 10 users, 2 devices, 8 h/day, 30 days; 5,000 tasks | 1,584,000 | 276.05 |

These are our calculations, **not billed network bytes**: compression, headers, Markdown length and other services change actual egress. Add initial/post-join reads, event-driven snapshots, protected-mutation follow-ups and retries. For the 5-user/1,000-task example, one extra snapshot/device per separated write at 100 writes/user/day adds ~7.64 GB, taking the illustrative decoded total to ~12.22 GB before startup/retries. Coalescing can reduce that; it is not a global cost cap.

Current [egress pricing](https://supabase.com/docs/guides/platform/manage-your-usage/egress) lists uncached allowances Free 5 GB, Pro/Team 250 GB, then $0.09/GB paid overage; cached egress has separate quotas/pricing. If **actual** uncached usage were 276.05 GB on an otherwise unused 250 GB paid allowance, that component alone would be about $2.34 overage. This excludes plan/compute/add-ons and other projects; decoded samples cannot establish that bill. Free quota excess is not unlimited free service.

Before activation, capture actual organization/project usage and approve a budget plus task/tab/bulk-write operating envelope. Monitor Realtime message/rate/auth errors, peak connections/joins, API latency/5xx/timeouts, WAL/disk/partition health, egress and growth/forecast. Assign a human owner and agreed stop thresholds (any cross-account exposure immediately; repeated normal-load rate errors or persistent visible/online catch-up failure pause rollout). Confirm what monitoring/alerts actually exist; local timestamps/tests are not production telemetry. Proposed quota checkpoints: 50/80/95%, adjusted to the approved plan and daily forecast. The [Pro spend cap](https://supabase.com/docs/guides/platform/cost-control) covers only certain usage and may restrict service at quota; it is not a fine-grained budget and excludes compute/PITR and other add-ons. Do not disable it or raise limits casually.

## 8. Recovery, rollback and manual acceptance

**Before writes:** approve backup coverage/retention, secure storage and restore authority; retain schema/ACL/default-ACL/role/publication snapshots and exact migration/artifact provenance. [Supabase backup documentation](https://supabase.com/docs/guides/platform/backups) says managed daily backups/retention depend on plan; Storage objects are not in database backups, and custom-role passwords need separate handling (our NOLOGIN helpers need none). Verify required external Auth/API/platform configuration and secrets can be restored through authorized procedures, without copying them into this report. Set explicit RPO/RTO and prove restoration to an isolated destination. Backup data export and restore need appropriate separate data-handling authorization, not merely catalog-read approval. PITR is not assumed enabled or a free substitute for rehearsing recovery.

A public-table-only dump is not proof of complete recovery: account/Auth state, migration ledger, role/default privileges, helper schemas after installation, and any external Storage/configuration dependencies need an explicit coverage manifest and successful authorized restore.

**Failed installation:** stop, record SQLSTATE/ledger/runtime state and confirm the failing transaction rolled back. Do not retry repeatedly through live lock contention, silently repair cycles, delete ledger entries or reset a user database. Earlier files may already be committed.

**Frontend rollback after private cutover:** deploy/reload the approved **api-only** artifact; verify complete authenticated reads, writes, account guards, interval/resume recovery and accepted latency. It does not undo DB hardening. Cached old clients require an explicit transition plan. Returning to raw mode is not a rollback when tasks are unpublished and must not reintroduce DELETE-ID exposure.

**Database recovery:** prefer a minimal reviewed fix-forward grant for a demonstrated missing dependency. Do not restore baseline GRANT ALL or broadly regrant PUBLIC function execution. If hierarchy/Broadcast enforcement removal is truly necessary, approve a bounded reverse plan with dependency checks and required write hold; remove only known added objects, never broad CASCADE. Dropping hierarchy protection reopens cycle risk. Restoring data from backup/PITR is an incident action that may discard later legitimate writes; freeze/reconcile writes and obtain separate approval. None of these migrations has a general automatic down script.

**Physical/manual acceptance still required:** two real devices/browsers; iPhone Safari foreground/background/lock/unlock and BFCache/pageshow; airplane-mode/weak-network loss and recovery; deadline/foreground-hang/ambiguous-save behavior; account switch/logout with delayed responses; old/new cached clients during bridge and rollback; 100/1,000 and the maximum admitted task count with long Markdown; stable UI ordering/overdue dates/project changes; error/retry usability with keyboard/VoiceOver/touch. Node stores and fake browser events do not establish physical-device behavior.
