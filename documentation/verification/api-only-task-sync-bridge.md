## Preserved behavior and limits

- Tasks still read/write through the existing authenticated RLS-protected Data API. Optimistic creation identity, atomic content updates, completion, planned/due dates, project assignment, ordering, deletion, queues, revision/tombstone protection and rollback remain unchanged. API-only creates **no task channel**, raw or private. Auth may still use network/session-refresh infrastructure; the absence of all websockets is not the acceptance criterion.
- Initial and manual reads use complete ID-keyset pagination in 500-row requests until an empty page, publishing only a complete snapshot. API-only uses the existing coordinator, session checks and visible/online safety reads. Online, pageshow and visibility recovery request catch-up; a fresh application starts its initial read. Hidden/offline periodic work pauses. Account switches clear old state and obsolete results cannot publish into the new account.
- Background snapshots retain their 30-second whole-snapshot deadline, cancellation and bounded retries. A genuinely pending foreground read/write still has no new timeout; foreground loading can delay catch-up. JS suspension, throttling, network latency/backoff and protected mutations mean **120 seconds is a target cadence, not a delivery SLA**.
- Same-device writes appear optimistically; other visible/online devices normally see changes on the next two-minute read, or sooner through manual Refresh task list / resume / reconnect. There is no instant cross-device task push in this bridge and no durable offline queue.
- ProjectsStore and AppShell retain their normal create/edit/refresh and delete_project RPC flow. Successful same-account project deletion explicitly refreshes tasks, including after same-account navigation; other devices recover task-to-Inbox changes through task snapshots. Project-tree metadata is **not** given a new polling/subscription mechanism: remote project name/tree changes follow existing project-loading behavior and may require an application reload. Do not confuse task recovery with an invented project Realtime guarantee.
- Every visible tab pays for complete reads: roughly `ceil(N/500)+1` requests per two minutes at the normal cap (one request for an empty collection), plus startup/manual/recovery work. Multiple tabs multiply reads; long Markdown increases response size. Existing modest-beta cost assumptions remain, without a new cache framework.

## Rollback boundary

**Before publication removal only:** if the raw task publication and its independently accepted prior compatibility still exist, an explicitly approved frontend rollback can restore the prior raw-mode build (or change the effective environment.ts setting back and rebuild). Verify the database path still exists first; a historical artifact alone does not prove it. Deploy through Pages with the same artifact/cache/fleet checks. This does not undo #70/#71, and accepts the known raw DELETE metadata/privacy limitations temporarily. A revert of an unused environment.prod.ts would do nothing.

**After raw task publication removal/private-only cutover:** never roll back to a raw-mode build or re-enable a raw DELETE feed as an expedient repair. It cannot receive the removed events, loses this bridge's periodic/lifecycle recovery, and re-enabling the feed reopens the known metadata exposure. Keep/redeploy a verified **API-only** artifact as the safe degraded rollback; task CRUD and authoritative recovery remain available without weakening private policies. Broadcast activation is a later separately approved environment.ts/build change after #75 and actual owner/foreign delivery checks.
