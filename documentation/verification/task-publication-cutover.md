## Proposed changes

Branch `codex/raw-task-publication-cutover`, from main after PR #80. Add [20261109050000_remove_raw_task_publication.sql](../../supabase/migrations/20261109050000_remove_raw_task_publication.sql), ordered between #71 and unchanged #75. This makes the security transition reviewable, reproducible and ledger-tracked instead of relying on undocumented manual DDL. No Angular runtime, task/project persistence, RLS, replica identity or production synchronization setting changes.

The migration is one bounded transaction (5-second lock wait, 30-second statement timeout). It locks tasks in SHARE ROW EXCLUSIVE mode and removes **only** explicit, unfiltered/full-column public.tasks membership from supabase_realtime. It preserves the publication, its options and all unrelated members/publications. It aborts for inheritance/partitioned tasks, ALL TABLES coverage, public-schema publication coverage, another task publication, row filters/column lists or unavailable publication-owner authority. With no raw membership it is a safe no-op, including a fresh environment with no publication. No new grants, SET ROLE, owner transfer, superuser requirement or production data rewrite is introduced.

Migration-history note: the new 050000 version is before the still-unreleased hosted #75, with no amendment to #75. Previously used disposable/local environments may already record 060000; do not assume normal chronological migration-up will insert an earlier version there. Recreate only positively owned disposable environments or review a separate reconciliation for shared environments. Do not use include-all/repair against an unreviewed ledger or infer that source merge rewrites any existing database.

PostgreSQL requires publication ownership for ALTER PUBLICATION; task ownership and CREATEROLE alone are insufficient ([PG17 ALTER PUBLICATION](https://www.postgresql.org/docs/17/sql-alterpublication.html)). The migration checks effective inherited owner authority rather than inferring it from a role name or ADMIN-only membership. A SET-only role membership does not automatically supply current owner rights; if the approved runner cannot execute this as-is, **stop for a separately reviewed operator/privilege plan**, not automatic elevation. Local negative ownership tests use a disposable fixture administrator only; production ownership is not changed by this proposal.

Publication membership removal is transactional ([PG17 publication](https://www.postgresql.org/docs/17/logical-replication-publication.html)). The table lock does not provide a universal administrator/publication-DDL mutex. Freeze unrelated publication/schema DDL during the controlled window, inspect independently after COMMIT, and retain #75's own publication preflight. Unknown operators can otherwise change topology after any check; the migration does not claim to constrain trusted administrators forever.

## Failure handling

- Preflight/ownership/topology mismatch: stop before writes. Do not recreate publications, adopt other objects, transfer ownership or grant roles automatically. Review a narrow remedy separately.
- Removal failure/timeout: its transaction must roll back; independently verify membership and ledger state before retry. Investigate contention and reschedule rather than raising timeouts. If removal committed but validation/#75 fails, **remain API-only** and hold the next stage; do not casually re-add the raw feed.
- Missing CLI ledger despite committed DDL requires incident review of runner/runtime provenance. Do not replay #70/#71, delete ledger entries, run migration repair or pretend SQL executed. No universal down migration is supplied.
- #75 failure: its transaction should roll back only its own helper/policy/trigger installation; verify that state and absence of unsafe residual memberships. Publication removal remains committed. Keep API-only reads/recovery and obtain a scoped fix-forward review. Do not broaden grants, weaken RLS/probe checks or return to raw mode.
- Sender/runtime delivery failure after successful install: task writes may still persist because notifications are best effort. API-only/manual/lifecycle/safety reads remain authoritative; keep that mode until evidence resolves the fault. Do not infer successful notification from SUBSCRIBED. Any backend fix/permission adjustment requires separate approval.
- After publication removal, raw-mode frontend rollback is **not a safe recovery**: it loses automatic interval/lifecycle catch-up and re-enabling the feed would restore the known metadata exposure. Retain API-only even if #75 must be repaired. Restoring task data is not a remedy for publication/ACL faults and would require a separate incident decision reconciling later writes.

Remaining operational risks include cached/dormant clients, native service/version drift and probe compatibility, future partition grants/exposure, publication DDL by administrators, best-effort notification gaps/rate limits, API read volume and foreground timeout/mobile suspension limitations. Local results do not authorize production execution or certify absence of all external consumers.
